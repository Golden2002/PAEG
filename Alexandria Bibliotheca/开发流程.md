## 流程总览（10 阶段 + 5 横切）

```
阶段1 立项 → 阶段2 需求 → 阶段3 架构 → 阶段4 环境 → 阶段5 开发循环
    ↑                                                        ↓
阶段10 复盘 ← 阶段9 维护 ← 阶段8 运维 ← 阶段7 发布 ← 阶段6 集成
    └─────────── 横切：文档驱动 / 质量内建 / 安全左移 / 12-Factor / 度量 ────
```

**核心循环**：开发(5) → 集成(6) → 发布(7) → 运维(8) → 维护(9) → 复盘(10) → 新需求(1)

## 阶段 1：愿景与立项

**目标**：明确"为什么做"——产品愿景、范围、成功指标、可行性。

**关键活动**：利益相关者访谈、可行性分析、风险评估、章程签署、路线图规划。

**产出物**：项目章程、愿景陈述、范围声明、可行性报告、RACI 矩阵。

**最佳实践**：30 秒"电梯演讲"、OKR/SMART 目标、明确"不做的事"。

**常见陷阱**：愿景模糊、范围蔓延、跳过可行性评估。

## 阶段 2：需求分析与规划

**目标**：把愿景拆解为可执行、可验证、可追溯的需求。

**关键活动**：需求收集、用户画像、用户故事（INVEST）、验收标准、优先级排序（MoSCoW/RICE）、需求评审。

**产出物**：需求规格（SRS）、用户故事地图、需求可追溯矩阵（RTM）、产品待办列表。

**最佳实践**：区分功能/非功能需求、每条需求必须可追溯测试、包含度量指标（"p95<200ms"而非"快"）。

**常见陷阱**：需求"冻结"不更新、粒度过粗、遗漏非功能需求。

**目标**：把需求翻译为技术蓝图——高层设计、技术选型、模块边界、API 契约。

**关键活动**：HLD/LLD、ADR（架构决策记录）、数据模型、API 契约先行、威胁建模。

**最佳实践**：ADR 模板（Context→Decision→Consequences）、YAGNI、安全左移（威胁建模）、契约先行。

**常见陷阱**：过度设计、不写 ADR、忽视非功能需求。

## 阶段 4：环境与流水线就绪

**目标**：开发前把工具就位——版本控制、CI/CD、测试基础设施、密钥管理。

**关键活动**：选分支策略（Trunk-Based/GitHub Flow）、搭 CI/CD、分支保护、Lint/静态分析、密钥管理、开发环境文档。

**产出物**：CI 配置、Dockerfile、分支保护规则、CONTRIBUTING.md、环境搭建脚本。

**最佳实践**：Pipeline as Code、分层测试（单元<1min/集成<10min）、快速反馈（PR 检查<10min）、环境隔离。

**常见陷阱**：先写代码后搭流水线、密钥硬编码、CI 跑 35 分钟。

## 阶段 5：开发循环（开发-测试-重构）⭐核心

**目标**：在保持代码健康的前提下高质量实现需求——TDD Red-Green-Refactor 循环。

**关键活动**：
```
1. 选需求/故事 → 2. 写失败测试(RED) → 3. 最小代码通过(GREEN)
→ 4. 重构(REFACTOR) → 5. 提 PR → 6. 代码审查 → 7. 合并 → 8. 部署测试
```

**产出物**：源代码、测试代码、PR、commit、CHANGELOG 条目。

**最佳实践**：
- **TDD**：测试先行，重构是开发的一部分（[Fowler](https://refactoring.com/)）
- **小 PR**：<400 行变更（[Google](https://google.github.io/eng-practices/review/developer/small-cls.html)）
- **代码审查**：1 个工作日内响应（[Google speed](https://google.github.io/eng-practices/review/reviewer/speed.html)）
- **Conventional Commits**：feat/fix/refactor/docs/test

**常见陷阱**：跳过测试/重构、大 PR、PR 躺一周没人看。

## 阶段 6：持续集成与交付

**目标**：自动汇聚变更成可发布产物——构建、测试、依赖扫描、镜像构建。

**关键活动**：自动化构建、分层测试、SCA 依赖扫描、容器镜像、SBOM、自动部署 staging。

**产出物**：构建产物、版本号、SBOM、测试报告、覆盖率报告。

**最佳实践**：构建一次到处部署（[Vercel](https://vercel.com/i/ci-cd-pipeline)）、流水线即代码（[Mergify](https://mergify.com/learn/cicd-pipeline)）、DORA 指标追踪。

**常见陷阱**：多次构建不一致、测试套件不分层、流水线失败没人管。

## 阶段 7：发布与部署

**目标**：把验证过的构建安全交付用户——版本管理、Release Notes、发布策略。

**关键活动**：SemVer 版本号、CHANGELOG、发布策略（蓝绿/金丝雀/特性开关）、回滚预案。

**产出物**：Git tag、CHANGELOG 条目、Release Notes、部署记录、回滚 runbook。

**最佳实践**：
- **SemVer**：MAJOR.MINOR.PATCH（[semver.org](https://semver.org/)）
- **Keep a Changelog**：Added/Changed/Deprecated/Removed/Fixed/Security（[keepachangelog](https://keepachangelog.com/)）
- **特性开关**隐藏未完成功能（[Fowler](https://martinfowler.com/bliki/FeatureFlag.html)）

**常见陷阱**：周五发布、无回滚预案、版本号乱编。

## 阶段 8：运维与可观测性

**目标**：让生产环境可见、可控、可调试——SLO、日志、指标、追踪、告警。

**关键活动**：配置 SLO/SLI、结构化日志（JSON+trace_id）、指标、链路追踪、告警分级、Runbook、On-call。

**产出物**：监控仪表盘、SLO 文档、告警规则、Runbook、值班表。

**最佳实践**：三支柱（Metrics+Logs+Traces）、结构化日志（[12-Factor XI](https://12factor.net/logs)）、SLO+错误预算、每个告警有 Runbook。

**常见陷阱**：部署完就完事、告警疲劳、无 Runbook。

## 阶段 9：维护与重构

**目标**：修复 bug、清理技术债、持续演进——不改变外部行为地改善内部结构。

**关键活动**：Bug 分类与复盘（5 Whys）、Hotfix、技术债清理、依赖升级、API 弃用、文档同步。

**产出物**：Bug 修复、Patch 版本、ADR、依赖升级记录、弃用公告。

**最佳实践**：**重构是日常编程的一部分**（[Fowler](https://refactoring.com/)）、依赖升级常态化、弃用流程（标 deprecated→等一版→移除）。

**常见陷阱**：只修 symptom 不查 root cause、"重构"偷换成"重写"。

## 阶段 10：复盘与持续改进

**目标**：从过程中学习，下个周期更好——Retro、Post-Mortem、流程优化。

**关键活动**：Sprint Retro（3 问：做好/做差/改进）、Blameless Post-Mortem、DORA 指标分析、Action Item 落地。

**产出物**：Retro 记录、Post-Mortem（Timeline/Root Cause/Action Items）、改进项 backlog。

**最佳实践**：对事不对人、Action Item 有 owner+deadline、DORA Quick Check（[dora.dev/quickcheck](https://dora.dev/quickcheck/)）。

**常见陷阱**：形式主义、只 blame 不改进、Action 无跟进。

## 横切关注点（贯穿所有阶段）

### A. 文档驱动开发（Documentation-Driven Development）

| 文档类型 | 创建阶段 | 负责 |
|---|---|---|
| 需求规格 | 阶段 2 | PM |
| 架构 + ADR | 阶段 3 | Tech Lead |
| API 文档 | 阶段 3/5 | 开发 |
| 测试记录 | 阶段 5/6 | 开发/QA |
| CHANGELOG | 阶段 5/7/9 | 发布 |
| 维护手册 | 阶段 8/9 | Tech Lead |
| 元能力沉淀 | 阶段 10 | 团队 |

**核心原则**：文档与代码同仓库（docs-as-code）、PR 一起审、**文档不迟于代码合并**。

## 分支策略（PAEG 推荐）

**Trunk-Based + 短生命周期 feature branch**：
```
main (永远可发布)
  ├─ feat/xxx (寿命<1天) → PR → CI → review → merge
  └─ hotfix/xxx (紧急) → 立刻合并
```
规则：main 永远可发布、分支<1天、合并需≥1 approval+CI 全绿、大特性用 feature flag、release tag 遵循 SemVer。

**📌 参考**：[技术全景「10.12 双远程仓库同步」](../PAEG技术全景文档.md)、[维护手册「18.22 Git Merge 冲突事故反思」](../维护手册.md)
