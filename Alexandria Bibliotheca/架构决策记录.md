## ADR-001：Agent 指挥 LLM 的工作机制

- 状态：Accepted
- 日期：2026-08-16（源自技术全景 §1.4）

### Context
教育智能体需要"教学全过程"的确定性控制，而非 LLM 一次性输出。

### Decision
**Agent 负责确定性骨架（装配/分片/路由），LLM 只负责文本生成**——教学循环（诊断/计划/讲解/评估/调整/反思）由 Agent 编排，LLM 在 Presenter 环节生成讲解。

### Consequences
- 教学流程可测试、可复现（确定性环节不依赖 LLM）
- LLM 只做最擅长的生成，质量与成本可控
- 评估用确定性启发式（不随机），调整用规则

## ADR-002：9 核心 subagent + ResourceLibrarian 架构

- 状态：Accepted
- 日期：2026-08-16（源自技术全景 §3.2）

### Context
教学涉及多个专业环节（诊断/计划/讲解/评估/调整/情绪/自我更新/个体化），需要职责拆分。

### Decision
**9 核心 subagent（Diagnostor/Planner/Presenter/Evaluator/Adapter/AnswerSolver/AffectionSupportor/SelfUpdateAgent/Individuality）+ ResourceLibrarian（资料检索）**，每个职责单一、上下文隔离。

### Consequences
- 职责清晰、可独立演进
- 上下文隔离防串扰
- 新增 subagent 需改 subagents.py（半侵入，下一步声明式化）

## ADR-003：Trunk-Based + 短生命周期分支策略

- 状态：Accepted
- 日期：2026-08-16（源自开发流程 §分支策略）

### Context
项目双远程（GitHub + ModelScope）、单人维护、演进快——需要简单可控的分支策略。

### Decision
**Trunk-Based + 短生命周期 feature branch（<1 天）**：main 永远可发布，合并需 ≥1 approval + CI 全绿，大特性用 feature flag。

### Consequences
- 简单、无长期分支
- main 始终可发布
- GitFlow 不采用（维护负担重，AWS 建议弃用）

## ADR-004：双远程仓库 GitHub + ModelScope

- 状态：Accepted
- 日期：2026-08-16（源自技术全景 §10.12 + 需求文档纪律 34）

### Context
项目需要 GitHub（国际）+ ModelScope（国内创空间）双端可访问、可恢复。

### Decision
**本地为权威源**：GitHub（sync_check.py API 通道）+ ModelScope（git push）双远程同步；任何交付前双端推送。

### Consequences
- 任一端可恢复整个项目（三处一致）
- 双远程推送是交付前置（纪律 34）
- 本地代理重置 git 协议 → GitHub 用 API 通道规避

## ADR-005：Docker 容器化（单容器）

- 状态：Accepted
- 日期：2026-08-16（源自技术全景 §10.11）

### Context
需要统一部署（本地/magio 创空间），manim 0.19 兼容 Python 3.12。

### Decision
**单容器（Python 3.12 + ffmpeg + manim 0.19 + 全部源码）**，放弃 manim 隔离 venv 换部署简化；端口 7860（魔搭固定）/5000（本地）。

### Consequences
- 部署简化、依赖统一
- 镜像较大（含 manim 系统库）
- 新依赖必须同步 requirements.txt（纪律 33）

## ADR-006：Harness 借鉴三角色契约层

- 状态：Accepted
- 日期：2026-08-16（源自技术全景 §10.20 + 需求文档 §3.46.2）

### Context
借鉴 deepseek-harness 30 项优化，其中三角色（Provider/Consumer）是核心架构范式。

### Decision
**先落地契约层（agent_trirole.py RoleContract），具体三角色化留待后续波次**——契约先行，实现渐进。

### Consequences
- 契约稳定，实现可迭代
- 具体化是 6-10 周长期蓝图（需用户确认）

## ADR-007：LLM 优先意图路由

- 状态：Accepted
- 日期：2026-08-16（源自元能力 §6.7）

### Context
意图识别需要兼顾准确性与可维护性。

### Decision
**LLM 优先 + 规则兜底 + 模式短路**——meta_router 15 意图，LLM 判断为主，规则防退化，用户模式选择短路。

### Consequences
- 意图识别准确（LLM 强项）
- 规则兜底防退化
- 模式短路省 token

## ADR-008：3 位掩码约束架构

- 状态：Accepted
- 日期：2026-08-16（源自元能力 §6.33 + 技术全景 §10.20）

### Context
教育约束需要精细分层（教学/考试/自由层），且要可动态调节。

### Decision
**3 位掩码（A 直接性/B 情绪/C 深度）L0-L8 约束分层**——约束引擎 6 API（layer_get/set/compose/always_active/self_evolve/feedback_adjust）MCP 化。

### Consequences
- 约束精细可控
- 动态调节（数据化）
- 学习曲线陡（需理解掩码语义）

## ADR-009：Evaluator 确定性启发式（反随机铁律）

- 状态：Accepted
- 日期：2026-08-16（源自技术全景 §1.6）

### Context
教学评估需要可复现、可测试，不能依赖 LLM 随机输出。

### Decision
**评估用确定性启发式（不随机可复现），LLM 只负责讲解生成**——掌握度分数基于规则计算。

### Consequences
- 评估可测试可复现
- 测试可断言精确分数
- LLM 不参与评估（防抖动）

## ADR-010：14.x 工具生态「唯一适配层」桥接模式

- 状态：Accepted
- 日期：2026-08-29（源自架构可扩展性评估 + infra/lang_plugin_bridge.py）

### Context
14.x 平级独立库（14.1~14.6）需接入主项目，但主项目不能硬依赖独立库（独立库缺失会导致主项目 import 崩溃）。

### Decision
**每工具一个「唯一适配层」桥接**（范本 `infra/lang_plugin_bridge.py`，5.5KB）：插件优先 `import paeg_lang_style` + 失败静默回退 PAEG 原实现（原文件永不删除）。独立库内部用 registry 模式（`register_generator` / `RuleRegistry.load()/watch()`）保持自我可扩展。

### Consequences
- 独立库可插拔接入，主项目零侵入
- 插件缺失时主项目仍可运行（静默回退，不阻塞生成链路）
- 每工具需一个薄适配层（非零适配，但成本一次性、有范本可复制）

### Alternatives
- 直接 `import` 独立库：依赖缺失即崩溃，弃用
- 统一插件管理器：当前规模过度设计，薄适配层已足够
