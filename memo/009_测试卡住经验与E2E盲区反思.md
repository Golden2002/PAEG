## 一、测试卡住经验总结（防再发生铁律）

### 已发生的卡住场景（3 次）

| # | 场景 | 根因 | 教训 |
|---|------|------|------|
| 1 | `pytest tests -q -k "paeg or subagent"` 180s 超时被杀 | tests/ 中大量用例**真实调用 DeepSeek LLM**（网络 + 慢响应），无 mock 无超时 | **LLM 依赖用例必须隔离**，不能混入快速回归 |
| 2 | `pytest tests -q` 全量 590s 无输出 | 同上，全量含 LLM 真实调用挂起 | pytest 只跑 `-m "not llm"`（或按文件白名单）；LLM 用例单列手动跑 |
| 3 | PowerShell `Start-Job` 启动服务器超时被杀 | Start-Job 与调用进程生命周期绑定，后台任务被回收 | **服务器一律用 `Start-Process -PassThru` 独立进程**（PID 可查、可杀、日志可读） |
| 4 | **新增**：health 返回旧版本 0.40.4 | 昨日遗留 python 进程仍监听 5000，双进程共存，请求打到旧进程 | **启动前必查端口**：`netstat -ano | findstr :5000`，杀干净再起；启动后必验 `/api/health` 版本号 |
| 5 | **新增（最严重）**：启动服务器命令卡 10 分钟-4 小时 | **PowerShell 5.1 `Start-Process -RedirectStandardOutput + -RedirectStandardError` 组合 bug**：子进程（server.py 常驻）持续输出时，PowerShell 等待子进程退出才返回 → 命令永不返回，用户端长时间无响应 | **启动服务器禁用输出重定向**：`Start-Process python server.py -WindowStyle Hidden -PassThru`（立即返回 PID）；日志改由后端自己写文件或启动后查 health 验证 |
| 6 | 网络检索链路串行卡顿 | web_search_multi 对 5 个联想词串行 × Bing 15s timeout ≈ 100s+，用户对话卡 10 分钟 | **并行检索**（ThreadPoolExecutor 4 线程）+ 整体硬超时 20s + Bing timeout 15s→8s（实测 2.7s） |

### 防再发生检查清单（每次跑测试前 30 秒）

```powershell
# 1. 端口清理（防旧进程污染）
netstat -ano | findstr :5000
#   有监听 → Stop-Process 杀光（保留最新那个）

# 2. 服务器启动（★禁 -RedirectStandardOutput/-RedirectStandardError：PS5.1 bug 会卡死等待子进程退出）
$p = Start-Process python server.py -WindowStyle Hidden -PassThru   # 立即返回，不卡

# 3. 启动后必验（防打到旧代码）
Invoke-RestMethod http://localhost:5000/api/health | select version
#   version 必须 = 当前版本号（如 0.44.0）

# 4. pytest 只跑非 LLM 用例（LLM 用例单列）
python -m pytest tests -q -m "not llm" -p no:cacheprovider --timeout=60

# 5. E2E 每次浏览器操作设短等待（wait_for ≤ 20s），失败即记录不重试

# 6. 涉及联网检索的验证（web_search_multi）：已并行化+20s 硬超时，可安全调用
```

## 二、用户报告的 3 类 bug 与根因

### B1. 各模式显示"已完成知识库检索"但不一定"网络检索"【设计如此，需澄清】

**结论：是设计，不是 bug。**

触发链路（server.py teach_stream L1406-1458）：
```
提问 → kb.resolve_node 命中? ──是──▶ 徽章="知识库检索"（不联网）
        │否
        ▼
本地 facts 库命中? ──是──▶ 徽章="知识库检索"（本地事实优先于联网，L1417-1419 接线缺口修复）
        │否
        ▼
should_search(短输入/非检索意图短路，L1443-1445) ──不通过──▶ 徽章="知识库检索"（不联网）
        │通过
        ▼
web_search → 成功? ──是──▶ 徽章="网络检索"
        │否
        ▼
徽章="知识库检索"（联网失败降级）
```

**设计意图**：本地事实优先于联网（避免短输入如"我猜是en"污染回答），知识库命中就不浪费 LLM/网络。

**遗留问题**：徽章只有单一值（"知识库检索"或"网络检索"），当两者都完成时用户看到"知识库检索"会误以为没联网。
**改进方向**（已纳入 P2）：徽章支持复合值"知识库+网络检索"。

### B2. 查资料按钮交互（ChatGPT 式悬浮选项）【UI 需求】

当前：输入框右侧"查资料"按钮 = 独立发送键，点击即发送检索请求。
期望：像 ChatGPT 一样作为**模式选项**（选择后悬浮在输入框上方作为指令标签），用户输入内容后回车发送。

**方案**（已纳入需求清单 P2，未在 v0.44 实施）：
- 输入框上方加"指令标签栏"：`查资料` 点击后置为激活态（悬浮标签"🔍 查资料模式"）
- 激活后输入内容回车 → 走 `/api/resources`（for_ppt=false）而非普通 chat/teach
- 再次点击或发送后自动取消激活

### B3. 联网检索资料贫乏 + PPT 无实质内容【P0 已修复】

**用户预期设计**（agent 设计文档声称）：收到联网指令 → LLM 联想多种多样查询词 → 回传检索工具 → 丰富网页。

**代码现状（根因）**：
1. `_llm_choose_retrieval_scope`（subagents.py L109）只生成 **1-3 个"简洁关键词"**——设计文档声称的"多样化查询词联想"**从未实现**（文档-代码漂移）
2. `_search_web`（subagents.py L821）只用 `keywords[0]` 调 **1 次** web_search，max_results=3 → 最多 3 条
3. snippet 截断 150 字符 → PPT 大纲只有标题（subagents.py L927-931 `ppt_outline` 只用 `s['title']`）

**v0.44 修复**（已完成）：
- `web_search_tool.py` 新增 `expand_queries()`：LLM 联想 n 个多样化查询词（定义/应用/例子/最新进展角度，无 LLM 时规则兜底）+ `web_search_multi()`：多查询逐一检索 → 合并去重（可达 12 条）
- `subagents.py _search_web` 改用 web_search_multi（n_queries=4, per_query=3, max_total=12），snippet 放宽到 500 字符
- `ResourceLibrarian.run` 传 llm/subject 供联想；`ppt_outline` 用标题+正文要点

**实测证据**（2026-08-11）：规则兜底路径 5 个查询词、返回 6 条带正文结果（原 3 条干 URL），耗时 4.9s。

## 三、为什么 E2E/测试管线没发现这些问题？【核心反思】

### 根因分析（5 层）

1. **测试断言只查"形状"不查"内容"**
   - E2E/契约测试断言 `sources` 存在、类型正确、状态码 200
   - **从未断言**：`len(web_sources) >= 5`、`snippet 长度 > 100`、`ppt_outline 含正文要点`
   - 3 条干 URL 也能通过所有现有断言 → 内容质量盲区

2. **设计文档-代码漂移无检测机制**
   - 设计文档（技术全景文档）声称"agent 联想多种提示词"，代码从未实现
   - 测试基于**文档预期**写断言，不基于**代码实际行为** → 文档吹嘘 = 测试通过
   - **教训**：文档-代码一致性应纳入 audit_check（如扫描关键函数注释声称 vs 实现）

3. **E2E 测试数据"太正常"**
   - E2E 用知识库命中概念（熵/负负得正）→ 走知识库路径不联网 → 测不到 web 分支
   - **教训**：E2E 必须含"知识库 miss 概念"（如自创词/冷门词）触发联网路径，且断言联网结果数量

4. **真实网络检索不稳定 → 测试跳过**
   - Tavily/Serper/Bing 依赖 API key + 网络 → 测试常 mock 掉 → 真实路径零覆盖
   - **教训**：网络检索必须有"mock 集成测试"（固定返回 12 条验证去重/截断逻辑）+ "真实冒烟测试"（低频手动）

5. **前端交互心智模型未测试**
   - 按钮是"发送键"还是"模式选项"——纯 UI 心智问题，现有 E2E 只测"点按钮有响应"
   - **教训**：需人工走查核心交互（本项目由用户使用发现）

### 防再发生措施（已同步 audit 检查项候选）

- [ ] audit_check 新增：`web_search_multi` 集成测试（mock 12 条验证去重/数量）
- [ ] E2E 场景新增：知识库 miss 概念触发联网 → 断言 web sources ≥ 5 且 snippet 非空
- [ ] 文档-代码漂移抽查：resource 检索"联想查询词"设计 vs `expand_queries` 实现
- [ ] 前端交互走查清单：发送键/模式选项/悬浮标签心智模型

## 六、为什么 E2E/测试没发现这些模式缺口？【补充反思】

1. **检索链路审计从未纳入测试管线**：测试只测"端点有响应"，从不验证"每个模式是否真的接了检索链路"——需要**链路存在性断言**（静态扫描每个模式入口的检索调用点）
2. **method 的 tools 缺失是"静默降级"**：不传 tools 不报错，LLM 只是没有联网工具——无异常无失败，测试全绿但功能缺失。**教训：功能完备性需要人工/静态审计，测试无法覆盖"没接的线"**
3. **B3 系列（检索贫乏/歧义/PPT 标题）是"内容质量"问题**：现有断言只看形状（sources 存在/类型对），不看内容（条数/正文长度/相关性/大纲结构）

**防再发生**（已建议 audit_check 扩展）：
- [ ] 模式检索链路存在性检查（6 模式 × 检索调用点，静态扫描）
- [ ] web_search_multi 集成测试（mock 12 条验证去重/过滤/条数下限）
- [ ] E2E 断言升级：联网触发时 web sources ≥ 5 且 snippet ≥ 50 字符
- [ ] method/answer 检索接入回归（断言 tools 参数存在）
