# 010 · 测试哲学升级：既测"功能有无"也测"功能好坏"（v0.44 → v0.45）

> 日期：2026-08-11
> 触发：用户实测发现核心功能（联网检索/PPT 生成）"能用但不好用"——检索条数少且
> 相关性差（偶发跑偏到无关主题）、PPT 只有标题没有实质内容。
> 而既有测试管线（audit_check + pytest 212 例 + Playwright E2E）全部通过。

---

## 一、核心诊断：为什么测试全绿但功能不好用？

**既有测试哲学：只测"功能的有无"（existence），不测"功能的好坏"（quality）。**

| 测试类型 | 现有断言 | 缺什么 |
|---|---|---|
| audit_check 40 项 | 路由存在 / 无裸 except / 有检索调用点 | 不验证检索**结果质量** |
| pytest 212 例 | API 返回 200 / sources 是数组 / 字段存在 | 不断言 sources **数量下限**、**相关性**、**内容长度** |
| Playwright E2E | 点按钮有响应 / 徽章出现 | 不检查检索**结果是否跑偏**、PPT **大纲是否围绕主题** |
| 契约测试 | 响应结构符合 schema | schema 只约束形状，不约束内容质量 |

**结论**：测试管线验证了"系统按设计连通"（架构正确性），但**从未验证"输出符合用户期望"**（质量正确性）。对 LLM 驱动的功能（检索/生成/教学），质量维度远比形状维度重要，而恰好是测试盲区。

---

## 二、本次暴露的质量问题（检索/PPT）

### Q1 检索条数不足且不稳定
- 现象：用户问"超导体的量子隧穿效应"，有时 3 条、有时 6 条、有时返回"什么是/游戏角色/AOL 邮件"等无关结果
- 根因链：
  1. 无 Tavily/Serper/Jina API key → 只能走 Bing HTML 兜底
  2. Bing 对**连续中文**分词差（L208 自述）→ 长查询返回无关结果
  3. `_shorten_query` 原实现按空格/标点切分 → 连续中文切不出词 → 拆短重试失效
  4. `_bing_search` 的 q_words 过滤按空格切分 → 中文只算 1 词 → 过滤失效/误杀
  5. LLM 联想查询词不稳定（每次不同，偶发跑偏）
- 已修：jieba 分词（_shorten_query/_bing_search 过滤）、web_search_multi 并行化 + 20s 硬超时、相关性过滤 + 规则兜底

### Q2 PPT 只有标题无实质内容
- 现象：PPT 用"用户提问做标题 + 网页标题做内容"，没有正文要点
- 根因：`ppt_outline` 原本是规则拼接的"标题列表"，`_parse_outline` 把每个网页标题解析成独立 slide
- 已修：for_ppt 时 LLM 基于检索正文生成"## 章节 + 要点"结构化大纲（LLM 不可用才规则兜底）

### Q3 相关性污染（语义歧义）
- 现象："约瑟夫森结"→ 检索到游戏《第五人格》角色"约瑟夫"
- 根因：Bing 对专有名词/缩写的中文歧义无消解
- 已修：web_search_multi 相关性过滤（核心词命中检测）+ 全过滤时规则核心词兜底重试

## 三、测试架构升级方案（v0.45 执行）

### 双维度测试矩阵（用户要求"既测联通又测代码层"）

```
维度 1：Agent 联通性（architecture connectivity）——已有
  ├─ audit_check：路由/模块/检索调用点存在性
  ├─ 契约测试：前后端接口对应、schema 形状
  └─ E2E：功能可触发、UI 有响应

维度 2：质量（quality）——新增
  ├─ 检索质量断言：
  │   ├─ sources 数量 ≥ 5（下限）
  │   ├─ 相关性：每条 snippet 与提问核心词有重叠（jieba 切词后）
  │   ├─ 内容充实：snippet 长度 ≥ 50 字符
  │   └─ 无污染：结果 title/snippet 不含明显无关词（白名单校验）
  ├─ PPT 质量断言：
  │   ├─ ppt_outline 含 ≥ 3 个 "## 章节"
  │   ├─ 每章节含 ≥ 2 个 "- 要点"
  │   ├─ 大纲主题与提问相关（核心词在章节标题中出现）
  │   └─ 生成的 .pptx 文件存在且 slides ≥ 3
  └─ LLM 输出质量：注入确定性校验（长度/结构/关键词）
```

### 落地方式
1. **pytest 新增 `test_quality_retrieval.py`**：mock 固定检索后端 → 断言数量/相关性/内容长度（确定性，不依赖真实网络）
2. **pytest 新增 `test_quality_ppt.py`**：给定固定 sources → 断言大纲结构
3. **Playwright E2E 升级**：真实检索时断言"已联网检索"徽章 + 资源卡片数 ≥ 5；PPT 生成后检查下载文件
4. **audit_check 新增维度**：扫描关键函数是否含质量断言（防未来回归）

### 测试环境分层
| 层 | 是否真实联网/LLM | 用途 | 频率 |
|---|---|---|---|
| 单元测试（mock 检索） | 否 | 确定性验证逻辑（过滤/去重/条数） | 每次提交 |
| 集成测试（真实 Bing 但 mock LLM） | 半 | 验证检索质量真实情况 | CI 每日 |
| E2E（真实全链路） | 是 | 验证用户体验 | 发版前 |

## 四、检索质量指标（可量化 KPI）

| 指标 | 当前 | 目标（v0.45） |
|---|---|---|
| 每次检索 sources 数量 | 1-6（不稳定） | **≥ 5，稳定** |
| 检索结果相关性（核心词命中率） | 30-60%（偶发跑偏） | **≥ 90%** |
| snippet 平均长度 | 67-150 字 | **≥ 200 字**（含正文摘要） |
| 检索耗时 | 2.7-100s | **≤ 8s**（并行 + 硬超时） |
| PPT 大纲章节数 | 1-5（主题漂移） | **≥ 3 且围绕提问** |

## 五、与既有测试架构的关系（用户原话要点）

> "我们已经解决了测试的架构问题，既要测试 agent 本身的联通，又要测试代码层"

- **Agent 联通测试**（已有）：验证"各模块与上下游真实联通、前后端接口对应、技术设计指标是否真实实现"（对应 memo/009 第五节模式审计）
- **代码层测试**（已有）：单元/契约/静态检视
- **质量测试**（本次新增）：验证"功能的好坏"——这是第三维度，与联通/代码层并列

三层架构：
```
质量层（好坏）    ← 新增：检索/PPT/教学输出的质量断言
  ↑
联通层（有无）    ← 已有：audit + 契约 + 模式审计
  ↑
代码层（正确性）  ← 已有：单元 + 静态 + 无裸 except
```
