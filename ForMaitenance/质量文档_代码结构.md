## 1. 模块化：单一职责 + 高内聚低耦合

### 1.1 质量标准

| 判定项 | 量化阈值 |
|---|---|
| **单一职责** | 一个文件只承担一类职责；模块公开 API 数 ≤ 10（不含 dunder） |
| **高内聚** | 模块内函数共享同一数据/概念（如 `subagents.py` 全部围绕"subagent 类 + 辅助函数"）；跨主题代码（教 + LLM + 路由 + DB）不应挤在同文件 |
| **低耦合** | 模块对外依赖 ≤ 5 个其它模块；通过接口而非实现耦合 |
| **可独立测试** | 任一模块可单独 `pytest` 而不必启动 Flask/LLM |
| **可独立替换** | 改一个模块不影响其它模块的导入路径 |

> **业界锚点**：SOLID 的 S（Single Responsibility）+ O（Open-Closed）。Robert C. Martin《Clean Architecture》指出模块边界由"变化轴"决定；同一变化轴的代码同居，反之分散。

### 1.2 PAEG 项目经验

**正例**：
- `llm_api.py` 把"模型接口"完全隔离：抽象 `ModelAPI` 基类 + `OpenAICompatModelAPI` / `AnthropicModelAPI` / `MockModelAPI` 三实现 + `auto_detect_model_api()` 工厂。`chat(system, messages, max_tokens, tools, tool_choice)` 是唯一公开签名，业务层只感知接口不感知厂商。
- `subagents.py` 里 `Diagnostor` / `Planner` / `Presenter` / `ResourceLibrarian` 各自一个类、`run(self, ...)` 唯一入口、返回固定 dict 形态——这是教科书式的单一职责。
- Phase 2 拆分后 `services/polish.py`、`services/steering.py`、`services/routing.py` 把"语言润色 / 学科 steering / 模式纠正"三个独立业务抽走，`server.py` 从 ~4500 行瘦到 ~4000 行（README §架构与维护）。这就是"低耦合 + 高内聚"的成果。

**反例 / 待改进**：
- `server.py` 仍把 6 个早退分支（接口自指涉 / 元问题 / 学习方法 / 出题 / 情绪 / 复合输入）内联在 `/api/teach` 内（行 580–769），每段 ~30 行 try/except/return——典型的"职责堆叠"。建议抽 `services/interceptors/` 包，每种意图一个拦截器类，统一 `Interceptor.run(learner, concept, llm) -> Optional[Response]` 接口。
- `subagents.py` L88–L230 的 `_llm_choose_retrieval_scope` + `_pre_retrieve` 把"LLM 规划 + KB 检索 + Library 检索 + 关键词清洗 + 兜底分词"全塞进一个文件 140 行函数里。检索本身就是子职责，应当拆 `lib/retrieval/{scope_planner,kb_searcher,library_searcher}.py`。
- `subagents.py` L260–L357 的 `_safe_chat_with_retrieval` 同时承担"注入检索 → 调用 LLM → 工具调用解析 → 兜底拼接"，违反单一职责；参照"流水线（pipeline）模式"拆为多个 `Step` 对象。

### 1.3 实施建议

1. **建立 `services/interceptors/` 子包**：把 `server.py` 6 个早退分支提到独立模块，每个文件 ≤ 80 行，统一接口：
   ```python
   class Interceptor(Protocol):
       name: str
       priority: int  # 数字越小越先执行
       def match(self, concept: str, learner) -> bool: ...
       def handle(self, concept, learner, llm, **ctx) -> Optional[Response]: ...
   ```
   落地步骤：① 抽取 6 个拦截类；② 在 `server.py` 用 `for ic in sorted(registry, key=lambda x: x.priority): ...` 替代 if-else 链；③ 测试覆盖每类意图。

2. **拆 `lib/retrieval/`**：把 `_pre_retrieve` 拆三段——`scope_planner`（LLM 选库）、`kb_searcher`（KB 检索 + snippet 截取）、`library_searcher`（Library 文件检索）。`subagents.py` 只调 `RetrievalPipeline.run()`。

3. **建立"模块清单表" `docs/MODULE_INVENTORY.md`**：每模块一行记录"职责 / 入口 / 依赖 / 状态（active/deprecated）"。每季度 review 一次，过期模块标记 deprecated 并给迁移路径。

## 2. 多层级：分层依赖单向流动

### 2.1 质量标准

PAEG 应该有 6 层（L1–L6），依赖只能向下（高层 → 低层），不可反向：

```
L1 用户层（GUI / 外部 agent）
L2 应用层（Flask server.py / 路由）
L3 业务层（services/ — routing / polish / steering / learner_session）
L4 主 Agent 层（paeg.py — 教学六阶段编排）
L5 Subagent 层（subagents.py — Diagnostor/Planner/...）
L6 基础设施层（infra/runtime — kb / library / llm / sessions / mcp）
L7 工具层（tool_registry / skills / MCP / 资源 IO）
```

**量化判定**：
- 任一层不可 `import` 上一层的任何符号（用 `pyright` / `ruff` 的 `TID` 规则检查）。
- 跨层调用必须经过"接口/协议"，不得直接拿具体实现。
- 一行 `import` 涉及 ≥ 4 层即视为"渗漏"。

> **业界锚点**：Hexagonal Architecture（Alistair Cockburn）的"端口与适配器"、Clean Architecture 的"依赖倒置"、DDD 分层。

### 2.2 PAEG 项目经验

**正例**：
- `server.py` L73–L86 通过 `infra.runtime` 集中获取 11 个单例（`get_llm / get_kb / get_paeg / get_mcp_client / ...`）。这是教科书式的"高层通过工厂拿依赖、不直接 import 实现"——`server.py` 不再 `from llm_api import ModelAPI`，而是 `llm = get_llm()`，单元测试时可注入 MockModelAPI。
- README §架构与维护 列出 Phase 1–4 拆分路线，正是"先把 server.py 拆薄、再拆 blueprints、再拆 agents"的渐进分层。
- `subagents.py` 内部 `Presenter` 类不直接调 `knowledge_base.KnowledgeBase.search`，而是持有 `self.kb` 引用（构造时注入），可替换为 mock KB。这是依赖倒置（DIP）的典范。

**反例 / 待改进**：
- `server.py` 仍混着 L2（路由）+ L3（业务）+ L6（直接 `import` lib.ingest.handlers）。具体证据：行 240–246 `from lib.ingest.intent_router import is_file_operation, route_intent, extract_filename`、`from lib.ingest.readers import read_corpus_full`、`from lib.ingest.retriever import make_retriever` —— 一个路由函数直接穿透 4 层到 `lib/ingest/`。建议把这堆 `from lib.ingest import ...` 抽到 `services/file_op_service.py`，让 `server.py` 只 `from services.file_op_service import try_file_op`。
- `subagents.py` L462–L529 的 `_execute_tool_calls` 是"工具调度器"——按理应属 L6/L7 工具层，但写在 L5 subagent 文件里。Phase 4 拆 `agents/tools/executor.py` 时应一并搬走。

### 2.3 实施建议

1. **加 pyright 严格模式 + TID252/TID251**：在 `pyrightconfig.json` 设 `strict = ["infra", "services", "agents"]`，禁止上层 `import` 下层的具体类（仅允许 `import` 接口/Protocol）。
2. **画"分层依赖图"**：用 `pydeps` 或 `importlinter` 自动生成 `docs/architecture_dependencies.png`，每次 PR 必查——新出现的"反向 import"立刻标红。
3. **server.py 渗漏清零**：grep 一下 `from lib.`、`from infra.`、`from tools.`、`from skills.` 在 `server.py` / `services/` 的出现次数，目标是 server.py 只 `from services.` 与 `from infra.runtime`（白名单）。

## 3. 参数化调用：高层把低层作为参数传入（核心重点）

### 3.1 质量标准

**这是用户最强调的维度。** 一句话规则：

> **高层模块不得直接 `import` 或 `new` 低层实现；低层实现必须以参数形式（函数/对象/类）从外部注入。**

| 判定项 | 量化阈值 |
|---|---|
| **依赖注入** | 任何 LLM/KB/工具/DB 调用都必须通过参数传入；不许在函数体里 `from xxx import yyy; yyy()` |
| **接口 vs 实现** | 参数类型用 `Protocol` 或抽象基类，不绑死具体类 |
| **可替换性** | 任意 swap 一份 mock 实现（mock LLM、内存 KB、假工具）就能跑通单测 |
| **构造期 vs 调用期** | 依赖在 `__init__` 注入；`run()` 内不可再 `import` |
| **工厂集中化** | 所有单例构造集中于 `infra/runtime.py` 等 1–2 个工厂文件 |

**经典范式**：
```python
# ✅ 高层只声明"我需要 X"，不管 X 哪来
def run_agent_loop(model: ModelAPI, tools: list[Tool], kb: KnowledgeBase) -> Reply:
    ...
# ❌ 反例：高层自己 new 一个具体类
def run_agent_loop() -> Reply:
    from openai import OpenAI
    return OpenAI().chat(...)  # 绑死厂商，无法测试
```

> **业界锚点**：依赖注入（Martin Fowler《Inversion of Control Containers》）、Hexagonal Architecture 的"port/adapter"、Spring/Guice/DI 容器思想。函数式编程里这就是"first-class function"——把行为当参数传。

### 3.2 PAEG 项目经验

**优秀正例**：
- `llm_api.py` 的 `auto_detect_model_api()` 工厂 + `ModelAPI` 抽象：业务层（subagents/server）只拿到一个 `ModelAPI` 实例，**完全不知道背后是 DeepSeek / Anthropic / OpenAI / Mock**。换厂商只需要改环境变量，业务代码零改动——这是 PAEG 最值得骄傲的参数化成果。
- `subagents.py` L571–L572 `class Diagnostor: def __init__(self, model, kb)`、`subagents.py` L653–L655 `class Presenter: def __init__(self, model, kb)`——所有 subagent 类都在构造期接 `model` 和 `kb`，`run()` 内不再 import。
- `Presenter.run(step, learner, previous, tone_info=None, concept=None, subject=None)`（L678–L680）——多个可选参数让调用方灵活控制；`set_pending_overrides()` 模式让上游 Adapter 决策"注入式"传进来（L664–L676），Presenter 用完即清（`_pending_style_override = None`）。这是教科书式的"参数化 + 一次性消费"。
- `tools/...` 里 `_safe_chat(model, system, user, ...)`（L99–L139）—— 整个文件最热的函数，纯函数式签名，LLM 实例完全由调用方注入；`_safe_chat_with_retrieval` 进一步把 `learner / llm` 也注入 `_pre_retrieval`，形成流水线。

**反例 / 待改进**：
- `subagents.py` L262–L271 `_safe_chat_with_retrieval` 调用 `_pre_retrieve(str(question), subject, learner=learner, llm=llm)`，参数化到位；但 L268–L272 内又用 `_kb = KnowledgeBase()` 自行 new 出 KB 实例——破坏了"高层不 new 低层"的规则。应该改成 `kb: Optional[KnowledgeBase] = None` 参数传入，调用方决定是否提供。
- `subagents.py` L907 `_search_kb` 与 L940 `_search_library` 在内部 `from knowledge_base import KnowledgeBase` / `import os as _os` 自行访问文件系统——这是"绕过参数化"的典型反模式。如果未来要切到 S3 / Postgres 检索，必须改这两个函数本体；正确做法是把 `KBRetriever`、`LibraryRetriever` 抽成 Protocol，构造函数注入。
- `subagents.py` L146–L230 `_llm_choose_retrieval_scope` 在函数体内调 `_safe_chat(llm, ...)`——llm 是参数传入的，这点对；但 L249 又调 `_llm_choose_retrieval_scope(question, llm, subject=subject)`，再到 L455 `_safe_chat_with_retrieval(self.model, system, user, subject=subject, max_tokens=512, tools=_tools, learner=learner, llm=self.model, ...)` 把 `self.model` 又当 `llm` 传了一遍。这暗示 `subagents.py` 里 `model` 和 `llm` 是同一个对象被反复传递——应该统一命名为 `model`（与 L571 Diagnostor 一致），删掉冗余参数。
- `server.py` L127 `paeg = get_paeg()` 把 PAEG 主 agent 当全局单例，后续所有路由都引用它；这把"主 agent 实例化时机"绑死在模块加载期，单元测试无法注入替代实现。正确做法：把 `paeg` 做成 `current_app` 扩展（`paeg.init_app(app)`），按请求上下文提供。

### 3.3 实施建议

1. **建立"参数化契约测试" `tests/test_param_injection.py`**：对每个 subagent 类，断言
   - `__init__` 不调任何 `import` 之外的副作用；
   - `run(...)` 内不出现 `import` 语句（用 AST 检查）；
   - 用 mock 替换任一参数，行为应可控变化。

2. **统一命名 `model` vs `llm`**：在 `subagents.py` 全文件 grep `llm=` 参数，全部改为 `model=`（与 Diagnostor/Presenter 一致）。提交一版"命名规范化" PR，不改逻辑只改名。

3. **拆 `RetrievalBackend` Protocol**：
   ```python
   class RetrievalBackend(Protocol):
       def search_kb(self, query, subject) -> list[Hit]: ...
       def search_library(self, query, learner_id) -> list[Hit]: ...
       def search_web(self, query, n) -> list[Hit]: ...
   ```
   `subagents.py` 只持有 backend 引用，构造期注入；本地 / S3 / Postgres 实现类可替换。

4. **把 `paeg = get_paeg()` 改为 Flask extension**：建立 `extensions.py` 暴露 `paeg_ext = PAEGExtension()`，`paeg_ext.init_app(app)` 注入配置；`server.py` 通过 `current_app.extensions["paeg"]` 取。这才能"换 main agent 不重启进程"。

## 4. 可扩展性：插件机制 + 声明式配置

### 4.1 质量标准

PAEG 应有四类扩展点：

| 扩展点 | 形式 | 判定 |
|---|---|---|
| **配置扩展** | JSON/YAML 配置（`paeg_modules.json`）开关模块 | 加新模块不改代码 = 通过 |
| **目录扫描** | skills/、hooks/、workflows/ 目录自扫描注册 | 放一个文件进目录 = 自动生效 |
| **注册装饰器** | `@tool / @skill / @subagent` 装饰器挂入注册表 | 加一行装饰器 = 通过 |
| **声明式工作流** | YAML / JSON 描述步骤序列、路由、并行 | 改 YAML = 通过，改代码 = 失败 |

> **业界锚点**：Anthropic Agent Skills `agentskills.io/specification`（目录扫描 + YAML 声明）、CrewAI `@CrewBase` + `agents.yaml` + `tasks.yaml`、LangGraph 声明式 StateGraph、OpenCode `<available_skills>` 注册表。

### 4.2 PAEG 项目经验

**正例**：
- `paeg_modules.json` 模块门控（README §12 模块化架构）：14 个功能模块可独立启用/禁用，上架下架不改代码——这是配置扩展的典范。
- `SkillRegistry` 扫描 skills/ 目录自动注册（`server.py` L176–L188、`subagents.py` L35–L65），新加一个 `SKILL.md` 即可被 LLM 看到——典型的目录扫描。
- `_inject_skill_catalog` 幂等性保护（L186）——已含 `## 可用技能` 标记就跳过，防止 SSE 多次 `generate` 重复注入。
- Phase 2 `infra/runtime.py` 集中 11 个单例（README §架构与维护），新增单例只需加一个 `get_xxx()` 函数，调用方不改——这是"注册表 + 工厂"的范式。

**反例 / 待改进**：
- 9 个 subagent（Diagnostor / Planner / Presenter / Evaluator / Adapter / AnswerSolver / AffectionSupportor / SelfUpdateAgent / Individuality）的编排是**硬编码**在 `paeg.py`，不在 `paeg_agents.yaml`。`PAEG架构设计标准.md` §六 关键结论 第 2 条已点名："用 agents.yaml / tasks.yaml 把 9 个 subagent 编排**数据化**"。
- workflow / hooks 当前不存在独立模块；`paeg.py` 的六阶段（诊断→计划→呈现→评估→调整→反思）是 `for step in plan: ...` 的硬编码序列，没有声明式工作流文件。
- 工具调用目前只 `get_tool_defs()` 简单列表（`subagents.py` L835–L839），没有按风险分级 / 角色权限矩阵。`PAEG架构设计标准.md` Oracle 评审 I8 = ❌ 缺失。
- skills 加载后没有按需 lazy load——`catalog_prompt()` 一次性把所有 SKILL.md 元数据塞进 system prompt（`subagents.py` L57）；tokens 长期偏高。`PAEG架构设计标准.md` S6 = ⚠️ 部分。

### 4.3 实施建议

1. **新增 `paeg_agents.yaml`**：
   ```yaml
   agents:
     - name: diagnostor
       class: agents.diagnostor.Diagnostor
       enabled: true
       triggers: [teach]
       outputs: [prerequisites_status, recommended_depth]
     - name: presenter
       class: agents.presenter.Presenter
       enabled: true
       tools: [web_search, solve_problem]
       risk_level: low
   workflows:
     teach:
       steps: [diagnose, plan, present, evaluate, adapt, reflect]
       parallel: false
   ```
   `paeg.py` 改为读 YAML 动态构造。投入 1–4h，扩展性 +30%。

2. **建立 `registry/` 目录**：把 `tool_registry` / `skill_registry` / `subagent_registry` 三个注册表统一接口（`register(name, obj)` / `lookup(name)` / `list()`）；新增一类只改一处。

3. **目录扫描加 hook 点**：在 `paeg_hooks/` 目录里 `on_teach_start.py` / `on_evaluation_failed.py` 等，启动时扫描注册成事件回调，参考 OpenAI Agents `tool_input_guardrails`。

4. **声明式权限矩阵** `permissions.yaml`：`agent → tool` 的允许/拒绝/需审批映射。LLM 调用 `web_search` 需审批，`solve_problem` 允许，`shell_exec` 禁止——参考 OpenCode `permission` 配置。

## 5. 可维护性：命名 + 注释 + 测试 + 文档

### 5.1 质量标准

| 维度 | 标准 |
|---|---|
| **命名一致性** | snake_case 函数、PascalCase 类、UPPER_SNAKE_CASE 常量；动词开头函数、名词开头变量 |
| **注释密度** | 每个公开函数 docstring + 关键决策点 inline 注释；超过 50 行的函数必须有分段注释 |
| **类型注解** | 所有公开函数有完整 type hints；内部可选 |
| **测试覆盖** | 核心链路 ≥ 70%；subagent 行为有 fixture；端到端冒烟必跑 |
| **变更留痕** | 关键 bug 修复带 commit message + 文档同步（README / CHANGELOG） |
| **文档同步** | API 改动必须在 `CHANGELOG.md` + `PAEG技术全景文档.md` 同步更新 |

> **业界锚点**：PEP 8 / PEP 257、Google Python Style Guide、refactoring.com 的"代码坏味道"清单、Working Effectively with Legacy Code（Michael Feathers）。

### 5.2 PAEG 项目经验

**正例**：
- `subagents.py` 每个函数都有 docstring，且**带版本号注解**（如 L142 `v0.22.1`、`L143` `# v0.26 ⭐ 需求B`），让接手者一眼看到"这函数 v0.22 引入、v0.26 增强"——这是高质量的注释留痕。
- `server.py` 行 1–17 顶部 docstring 列出全部 API 契约 + 启动命令——任何接手者读完这段就能跑起来。
- `LLMResponse` dataclass（`llm_adapter.py` L26–L34）显式字段：`text / stop_reason / input_tokens / output_tokens / latency_ms / provider / model`——可观测性内建。
- README §检视命令 定义了 5 个铁律命令（audit_check / smoke_test / pytest / sync_check / arch_check），把"质量门"具象化。
- `_safe_chat` 失败返回 `None` 而非 raise（L138）——上层可优雅降级到规则模板，不炸流程（对照 `PAEG架构设计标准.md` G5）。

**反例 / 待改进**：
- `subagents.py` 长达 ~1100 行，单文件 9 个 subagent 类 + 20+ 辅助函数，难快速定位。建议按 subagent 拆 `agents/{diagnostor,planner,presenter,evaluator,adapter,answer_solver,affection_supportor,self_update,individuality}.py`，每个 ≤ 150 行。
- `subagents.py` 多处 `pass  # pass` 双 pass（L228–L229、L323–L324、L350–L351、L390–L391、L759–L760、L772–L773、L784–L785）——明显是历史 try/except 留下的死代码，应删。
- `server.py` / `api/teach` 6 个早退分支的 try/except 全用 `except Exception as _e: print(...)`（如 L575、L601、L611、L637、L697、L728）——`audit_check.py` 必报警告。建议统一 `except SpecificException` 并 `logger.warning(..., exc_info=True)`。
- 测试覆盖：README 提到 `132 个测试` 但 README 没列覆盖明细；subagent 行为无独立 fixture 测试；建议 `tests/agents/` 镜像 `agents/` 结构，每 subagent 至少 5 个单测。
- 没有 `pytest.ini` / `conftest.py` 的 fixtures 中心化管理；测试应集中提供 `mock_llm / temp_learner / kb_factory`。

### 5.3 实施建议

1. **拆 `subagents.py` 为 `agents/` 包**：按类拆 9 个文件 + `agents/__init__.py` 导出 `__all__`。零行为变化——纯搬家，每文件拆完跑 `pytest tests/` 验证。
2. **删双 `pass` 死代码**：grep `^        pass$` 在 `subagents.py` + `server.py` 出现处，逐条删除（保留 try/except 框架即可）。
3. **建立 `tests/conftest.py` 中心 fixtures**：
   ```python
   @pytest.fixture
   def mock_llm(): return MockModelAPI()
   @pytest.fixture
   def sample_learner(): return LearnerProfile(id="test_001", grade_level="high_school")
   @pytest.fixture
   def kb_with_sample(): return KnowledgeBase.from_json("tests/fixtures/sample_kb.json")
   ```
4. **写 `docs/NAMING_CONVENTIONS.md`**：动词/名词规则、版本号标注规则（`v0.X ⭐ P0/P1`）、模块公开 API 数量上限。
5. **CHANGELOG 强制 hook**：pre-commit 钩子检测 `server.py / subagents.py / prompts.py` 改动后自动提醒 "是否更新 CHANGELOG.md"。
